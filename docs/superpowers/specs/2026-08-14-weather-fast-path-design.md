# 天气快速回答与追问承接设计

## 背景

真实两轮复现显示，天气接口已返回当前温度、体感温度、湿度、风力和当日高低温，但主模型转述时丢失了部分字段。“具体点”没有被当作天气追问，因此第二轮未携带实时天气上下文，模型生成了无来源的低温和紫外线信息。两轮端到端耗时约为 7.8 秒和 11.7 秒，主要消耗在主模型与后续质检。固定的“最困扰你的是什么”话术来自结构化输出失败降级，与当前话题无关。

## 目标

- 天气首轮回答完整包含天气现象、当前温度、体感温度、最高/最低温、湿度、风力和降雨提示。
- “具体点”、“详细点”等紧跟天气回答的短追问继承上一轮城市和日期，不编造数据。
- 天气快速路径不调用主模型或副模型；缓存命中时应接近即时，首次查询只受天气接口耗时影响。
- 结构化输出失败的普通降级话术保持话题中性，不再默认转向情绪困扰。

## 方案选择

### 采用：确定性天气快路径

在安全输入预检后识别天气查询及其短追问，直接使用 `LiveContext` 中的结构化天气内容构造 `AgentResult`。这条路径不进入知识库、主模型、副模型或重写链路。优点是快、字段稳定、不会幻觉；代价是天气话术由程序模板维护。

### 未采用：仅调整 Prompt

要求模型完整复述天气字段。改动小，但仍需两次模型调用，无法保证字段不丢失，也无法稳定解决短追问中的无来源补全。

### 未采用：只增加缓存

可减少天气接口耗时，但主模型和副模型仍为串行瓶颈，且“具体点”仍不会触发天气查询。

## 设计

### 天气意图与追问

新增一个纯函数，根据当前消息和最近一组用户/助手历史判断有效天气查询：

- 当前消息本身包含天气关键词时，直接使用当前消息。
- 当前消息是“具体点”、“详细点”、“再说说”、“那明天呢”等有限白名单追问，且最近一轮明确是天气话题时，由上一轮提取城市并合成查询。
- 不满足上述条件时不猜测话题，继续原有对话链路。

追问不引入跨会话状态，只使用已传入 `chat` 的受限历史，避免额外持久化和串话。

### 回答与安全边界

快路径保留现有 `precheck(user_text)`，危机、诈骗和越权输入仍优先按现有确定性规则处理。天气回答只来自天气接口映射和程序模板，因此不需要再做模型质检。返回的 `intent` 固定为 `chat`，`action` 为 `null`，保留 `live:weather` 来源和阶段耗时。

回答顺序固定为：天气现象与当前温度，体感，高低温，湿度与风力，最后给出有数据依据的降雨提示。不推断接口未返回的紫外线、空气质量或生活指数。

### 失败降级

天气接口超时、返回非法数据或缺少目标日期时，保持现有联网搜索与模型链路，不伪造实时结果。普通模型结构化输出失败话术改为：“我刚才没能把这句话接稳。请再说一次，我会接着刚才的话回答。”超时、限流和网络失败继续使用各自的明确话术。

## 测试与验收

- 单元测试覆盖天气首问进入快路径，主模型和副模型调用次数均为零。
- 单元测试覆盖“具体点”继承沈阳天气，返回内容与实时来源一致。
- 单元测试覆盖无天气历史时的“具体点”仍进入普通对话。
- 单元测试覆盖天气接口失败时的原链路降级，以及新的中性 JSON 失败话术。
- 运行相关定向测试和完整 `pytest` 回归。
- 真实两轮验收时，首轮不丢字段，第二轮不出现无来源数据；缓存命中的追问不触发任何模型调用。
